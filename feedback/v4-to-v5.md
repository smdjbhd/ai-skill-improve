# v4 → v5 反馈

> 被评估对象：`output/v4/generated.md`（28 项检查全过）+ `output/v4/human-edited.md`（4 条批注）
> 结论一句话：**v4 的 18 条规则一条都不省钱，但一条都不省人——它们全靠我手工跑临时脚本，脚本还每轮重写一遍。v5 该把"检查"从流程里搬进 skill 里。**

## 一、v4 做成了什么

| 项 | 结果 |
|:---|:---|
| C1–C12 | 全过（结构没被附录 C 弄乱） |
| C13 | 附录 C 19 行，四列齐全，出处全部是"教材第 X 章「节名」" |
| C14 | 15 个中文别名零命中 |
| C15 | 无类比代替定义（`> AI 原话` 引用块除外） |
| C16 | 10 个算法首现句三件套齐全 |
| C17 | 8 个骨架概念全在术语表 |
| C18 | 3 条被否定的错句只以 `> AI 原话｜` 形式存在 |
| 人工批注 | 4 条，全部指向"检查器测不到的地方" |

## 二、v4 暴露的真问题：规则的执行力全靠人

### 问题 1：每轮都在重写检查器

- v3 写了 `tmp/check_v3.py`（166 行，20 项）；
- v4 又写了一份 `tmp/check_v4.py`（约 230 行，28 项），**大半是从 v3 复制粘贴改的**；
- 两份都在仓库外面（`default-workspace/tmp`），既没进 git，也没法给别人用。

这不是"多花点时间"的问题。**检查器是 skill 的一部分，不该是临时工。**

### 问题 2：检查器自己有 bug，而且 bug 比报告的错误更隐蔽

v3 第一版检查器连挂 10 项，其中至少 4 项是检查器写错：

| 现象 | 真实原因 |
|:---|:---|
| "节点里还有 `GB/T`" | `str.replace` 只换第一处 |
| "来源格式不对" | 正则没容忍反引号 |
| "对话表 0 个" | 表格分隔行是 `\|:---:\|`，不是 `\|---\|` |
| "行号超出 27 行" | 引了原始日志行号，不是摘录文件行号 |

**检查器没被检查过，它报的 PASS 就不可信。** 而 v4 又继承了这些问题（C4/C6/C7 的写法原样照抄）。

### 问题 3：一个藏了两轮的统计口径错

C2 要求"每节字数在区间内"。检查器的 `sections()` 只按 `## ` 切分，于是**最后一节（作业提交要求）会把后面三个附录全算进去**：

- v3 报 392 字（20–400 的区间，勉强压线过）；
- v4 因为附录 C 长了，一下变成 1377 字，直接 FAIL；
- 真正的原因是这一节只有清单，正文不到 200 字。

也就是说，**v3 的"20/20 全过"里，有 1 项是靠附录内容凑出来的**。这种错没人肉眼看得出，只有把检查器当代码去 review 才会发现。

### 问题 4：v4 的 C5 和 C18 一开始是矛盾的

C5（§3 引用的句子要在 §2 命中）与 T6/C18（被否定的句子不能在 §2 里）**逻辑上不可能同时成立**。这个矛盾不是写规则时发现的，是**写检查器时被逼出来的**——因为没法同时写出两个都通过的断言。

结论：**规则之间会互相打架，而检查器是唯一能把打架暴露出来的东西。**

### 问题 5：v4 抓不到的那 4 条人工批注，全都指向同一类

| 批注 | v4 为什么不报 |
|:---|:---|
| "混淆/扩散"只在术语表有定义，正文空转 | C17 只查"在不在表里"，不查"在正文有没有落点" |
| "攻击模型"三种名字没讲清分界 | 同上 |
| 导图节点"对称与流密码"漏了分组密码 | C4 只数长度和符号，不看含义 |
| 术语表"工作模式"把四个缩写当定义 | C13 只判"列非空、出处合法" |

规律很清楚：**能数出来的 v4 都管住了；"这一句到底有没有说清"这类判断，v4 一条都管不了。** 但其中前三条其实是可以半自动化的——比如"术语表里的词在正文的首次出现句里，必须能找到一个具体的例子词（S 盒、移位、唯密文、CBC 之类）"。

## 三、给 v5 的 6 条要求

### V1 检查器进仓库

- `skill/v5/scripts/check.py`，一条命令：`python skill/v5/scripts/check.py output/v5/generated.md`；
- 输出格式固定：`PASS/FAIL <规则ID> <人话说明>`，最后一行 `总计 N 项，失败 M 项`；
- 退出码：全过 0，有失败 1。这样能直接进 CI 或 pre-commit。

### V2 检查器必须能证明自己会失败

- `--self-test` 模式：内置 3 份"故意写坏"的样本（缺章节、术语混用、数值缺单位），要求检查器对它们**必须报 FAIL**；
- 判定：`check.py --self-test` 输出 3 个 FAIL，退出码 0（自测通过）；
- 理由：一个永远 PASS 的检查器比没有检查器更危险。

### V3 规则与实现一一对应

- 每条 Cn 在 `check.py` 里有一个同名函数 `check_cN()`；
- 跑完打印"已实现/未实现"清单，`skill.md` 里有的规则而 `check.py` 里没有的，必须显式报"未实现"，不许静默跳过。

### V4 失败要能定位

- 每个 FAIL 至少给一处 `文件:行号` 或行内容片段；
- 禁止只输出"不合格"三个字。

### V5 只用标准库

- Windows 上没装第三方包也能跑（本机 Python 3.12 + 标准库）；
- 不许依赖 `pip install` 的任何东西，也不许调用 `openssl`。

### V6 规则表只维护一份

- 别名组、骨架概念、数值三件套的算法清单，**从 `skill/v5/skill.md` 的表格里解析**，不许在 `check.py` 里再抄一遍；
- 判定：改 skill.md 里的别名表，`check.py` 的行为跟着变，不需要改代码。

## 四、v5 不要做的事

1. **不要**为了"能自动化"把判定放宽（例如把 C13 的"出处合法"降级成"出处列非空"）；
2. **不要**把所有规则都硬编码进 py，那样 skill.md 就变成了文档、py 变成了真相，两处维护迟早不同步；
3. **不要**引入 pytest/unittest 框架——单文件脚本更适合这个场景（要能直接扔进仓库、双击可跑）。

## 五、v5 的验收方式

1. `check.py output/v4/generated.md` 跑出 28 项 FAIL/PASS，与手工结论一致；
2. `check.py --self-test` 三个坏样本全被抓住；
3. 把 `skill/v5/skill.md` 的别名表临时加一个假别名（如"哈希值函数"），不改代码重跑，检查器能报出它；
4. 全程不联网、不装包。
