## 我读完记下的关键点

- **CSP 不是一个头文件，是一个签过名的独立模块**（DLL + 签名）。真正的密钥生成、随机数、加解密都在里面做，
  应用拿到的是句柄（`HCRYPTKEY` / `HCRYPTPROV`），不是密钥本身。所以"密钥不离开 CSP"是设计目标，不是口号。
- **三层结构**：应用程序 → CryptoAPI（`wincrypt.h`，链接 `advapi32.lib`）→ CSP。
- **密钥容器（Key Container）是按 Windows 用户账户隔离的**。同一个人换了登录账户就找不到原来的容器，
  报 `NTE_BAD_KEYSET`；服务程序要用 `CRYPT_MACHINE_KEYSET` 才能跨会话。
- **提供程序类型（Provider Type）**：`PROV_RSA_FULL`（最常用）、`PROV_DSS`（只做 DSS 签名）、
  `PROV_RSA_SCHANNEL`（TLS 用）。`CryptAcquireContext` 的 `dwProvType` 就是选这个，选错后面算法用不了。
- **两类密钥别混**：`AT_KEYEXCHANGE` / `AT_SIGNATURE` 产生的是长期公钥密钥对（存容器里）；
  传 `CALG_RC4` / `CALG_AES` 这类算法 ID 产生的是一次性会话密钥。加密文件一般是"会话密钥加密数据 + 公钥包会话密钥"，
  这就是第 10、11 章数字信封的雏形。
- **9.9 的五类函数**：服务提供者（`CryptAcquireContext` / `CryptReleaseContext`）、
  密钥产生与交换（`CryptGenKey` / `CryptDeriveKey` / `CryptImportKey` / `CryptExportKey`）、
  编码解码（`CryptEncodeObject` / `CryptDecodeObject`）、数据加解密（`CryptEncrypt` / `CryptDecrypt`）、
  哈希与签名（`CryptCreateHash` / `CryptHashData` / `CryptSignHash` / `CryptVerifySignature`）。
- **典型流程**：`CryptAcquireContext` 拿句柄 → `CryptGenKey`/`CryptDeriveKey` 生密钥 →
  （可选）`CryptCreateHash` + `CryptHashData` → `CryptEncrypt` → `CryptDestroyKey` → `CryptReleaseContext`。

## 我这周真做的实验（Visual Studio 2022）

1. 照 9.8 搭环境：包含 `wincrypt.h`，链接 `advapi32.lib`。
2. 写小程序：取 CSP 上下文 → 建 MD5 哈希对象 → 对一段测试字符串求哈希 → 打印。
3. 踩了两个坑，报错原文见下（这两个是我这周报告里 §6 的内容，不是我事后编的）：

```
error LNK2019: 无法解析的外部符号 __imp__CryptAcquireContextA@20
error LNK2019: 无法解析的外部符号 __imp__CryptCreateHash@20
```

```
CryptAcquireContext 返回 FALSE，GetLastError = NTE_BAD_KEYSET (0x80090016)
```

4. 修法：`#pragma comment(lib, "advapi32.lib")`；`CryptAcquireContext` 失败且错误码是
   `NTE_BAD_KEYSET` 时，带 `CRYPT_NEWKEYSET` 再调一次建容器。
