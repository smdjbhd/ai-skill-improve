## 二、本轮踩的坑（比改动本身更值钱）

### 1. 验收条件自己也需要被验收

第一版判定方法写完后，用 `tmp/check_v3.py` 跑，**连挂 10 项**，其中一半是判定方法本身写错：

| 症状 | 真实原因 |
|:---|:---|
| C2 报"作业提交要求 322 字不合格" | 我随手写的区间 `20–300` 没有依据，正文本来就 400 字左右 |
| C4 报节点里还有 `GB/T 39786` | 我用的替换只替换了第一处，导图里那两处没动 |
| C6 报"来源格式不对" | 判定正则要求字符串以路径开头，而正文写的是 `` `路径` ``（带反引号） |
| C7 报"对话表 0 个" | 正则没考虑表格分隔行是 `\|:---:\|` |
| C10 报"现象段有 2 行日志里找不到" | 规范说的是"代码块里的内容要原样"，我却把叙述句也算进去了 |
| C11 报"行号超出 27 行" | **摘录文件保留了原始日志行号（`11376\|`），我直接引了原始行号**，而文件只有 27 行 |

结论：**判定方法要精确到"匹配什么、从哪开始数、引哪份文件的行号"**。只写"要有来源""要能核对"都还不够——那只是把 v2 的毛病换了个说法。

### 2. 一个真实的反直觉发现：`bash -n` 拦不住这个 heredoc 坑

排查问题 1 时顺手跑了 `bash -n ~/bestidiocs4stu/sh/opensslinstall.sh`，输出：

```
行 87: 警告： 立即文档在第 55 行被文件结束符分隔（需要 "EOF"）
exit=0
```

**只报警告，退出码仍是 0**。所以"写完脚本先 `bash -n`"不能当作这类问题的防线。这条已写进 v3 的 §6 问题 1 结论里（`output/v3/generated.md` 问题 1 结论段）。

### 3. 摘录文件的行号陷阱

`handmade/lab/logs/01-*.log` 是摘录，正文每行前面带 `11376|` 这样的原始行号。于是"第 11376 行"有两种含义：原日志的第 11376 行、摘录文件的第 17 行。v3 的写法是：**引用一律用摘录文件的行号**，原始行号只在括号里说明。C11 就是按这个规则校验的。
